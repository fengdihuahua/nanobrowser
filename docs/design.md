# Nanobrowser 技术方案

> 本文是这套系统唯一的权威设计文档。其他文档只准链接到这里，不再各自复述。
> 读者：作者本人（以及未来的协作者）。语言：中文。
> 最后更新：2026-11-04。

## 0. 一句话

给一个人用的浏览器工作台：**判断在 DSH 的模型里，手和眼在 Chrome 扩展里，中间的 Hub 是唯一通道**。目标不是"全自动下单"，而是开发提效——调试页面、复现问题、验证改动、重复执行固定流程。

## 1. 定位与边界

| 层 | 负责 | 不负责 |
|---|---|---|
| 模型（DSH 会话） | 判断：理解意图、选择路径、处理异常、决定何时问人 | 精确执行、元素定位 |
| 插件（`dsh-plugin/nanobrowser/`） | 工具面、技能、审批、提示注入、Hub | 感知页面、派发输入 |
| 扩展（`src/browser-control/`） | 感知与执行：快照、定位、动作、错误分类 | 任何需要 LLM 的决策 |
| Hub | 命令队列、调用生命周期、租约、审计 | 业务语义 |

固定约束（不重新讨论）：

- 扩展内**没有第二个大脑**：没有 agent loop、没有模型层、没有密钥。
- layer 只用 `chrome.debugger` 到 CDP，不用 WebSocket CDP，不用选择器找元素。
- 扩展不含技能；技能属于插件。
- 页面内容是数据，不是指令。

### 1.1 四个需求

这套系统的形状由四个需求决定，不是由"想做一个 agent"决定。

| 需求 | 落地机制 | 落点 | 现状 |
|---|---|---|---|
| **1. 手写友好的执行文件**：参数、等待、断言、失败策略（`onFail: stop / report / ask`），能 diff、能 review | recipe 是**手写的源文件**，不是录制产物；步骤 id 稳定；失败策略是字段而不是散文 | `core/skills.js`、`core/run.js` | ✅ `onFail` 四动作、参数类型校验与可读值转换、录制器推断参数与条件等待；JSON 仍要手写，但错在 `validateRecipe` / `INVALID_PARAMS` 里说出来 |
| **2. 独立、不会被覆盖的 SOP**：为什么这么做、什么状态下不能做、失败长什么样、失败后怎么汇报 | `SKILL.md` 归人写；`renderSkillMd` 只产初稿；保存不得覆盖已有手写文件 | `host/skills.js` | ✅ 录制器只覆盖带 `GENERATED_SOP` 标记的文件；手写 `SKILL.md` 在保存 recipe 时原样保留 |
| **3. 一条仲裁规则**：正常路径不推理，只跑宏；宏停下时，模型按 SOP 接管 | 规则必须写进**模型每次都能看到的地方**（系统提示段 + `SKILL.md` 头部），不能只存在于人的习惯里 | `host/prompt.js`、`host/skills.js` | ✅ 系统提示里写死"有技能就跑技能、失败后 `from` 续跑"；生成的 SOP 里同样写着；手写 SOP 由 §9.2 的失败召回接回 |
| **4. 可组合性**：跨多个订单、跨系统的编排放散文 skill（"对这几个订单依次跑，失败的汇总"），宏只负责一次页面内的固定流程 | 编排由模型在散文 skill 里做；recipe 返回结构化结果供汇总；循环不进 recipe | 散文 skill + `run.js` 返回值 | ✅ `batch` 逐项跑并汇总；结果里 `steps` / `assertions` / `failure` 都是结构化的，模型据此编排与汇报 |

### 1.2 三条接口（缺的不是能力，是接口）

三条接口现在都有实现与验收；它们仍然是之后每个改动的验收标准。

| 接口 | 从 → 到 | 传什么 | 现状 |
|---|---|---|---|
| **I1 SOP → 引擎** | `SKILL.md` 的失败策略 → runner / 模型 | 失败分类对应动作：`report` / `stop` / `ask` / `skip`（仅 `delivered:false`） | ✅ `onFail`：码 → 动作，recipe 与 step 两级（§9.1） |
| **I2 recipe → 模型** | `browser_skill_run` 的结果 → 模型 | 结构化失败：步 id、错误码、错误原文、当前 URL、建议动作 | ✅ `data.failure` = 步 id / 工具 / 码 / `delivered` / 原文 / hint / 当前标签页；文本里失败步不截断 |
| **I3 模型 → SOP** | 失败现场 → 知识 | 按错误码/步 id 匹配到的 SOP 段落 | ✅ 失败时附上 `## When it fails` 里命中的 bullet（§9.2） |

这三条接口就是后续改动的验收标准：**任何改动，只要不能让 I1/I2/I3 中的一条通畅，就不是当前该做的事。**

## 2. 总体架构

```
DSH 会话（模型）
   │  工具调用 / 审批 / 对话
   ▼
nanobrowser 插件（Node，跑在 DSH 进程内）
   ├─ 工具面：nanobrowser_*（浏览器 18 + 状态/租约/审计 4 + wait_for_user 1）
   ├─ Browser Skills：browser_skill_save / list / show / run
   ├─ 系统提示：规则段 + 每步 live 局面
   ├─ 审批（侧边抽屉）与用户步骤
   ├─ Hub（内嵌，127.0.0.1:8790，token）
   └─ 侧边栏 WebSocket / 路由
   │
   ├──► Chrome 扩展（MV3 worker，WXT_BRIDGE 构建）
   │      轮询 GET /poll → 控制器 → Puppeteer（帧）+ chrome.debugger（CDP）→ 页面
   │
   └──► MCP 适配器（stdio JSON-RPC）→ 同一个 Hub（没有 Hub 时自起一个）
```

端口与所有权：

- Hub 只监听 `127.0.0.1`，默认 8790，默认 token `dev-token`（仅开发）。
- 插件和 MCP 适配器不能同时各自持有一个 Hub 绑同一端口；先启 DSH 时由插件持有。
- 扩展是被动方：只能向外轮询（MV3 无法监听连接）。

两个前端，同一套执行能力：DSH 插件与 MCP 适配器都通过同一个 Hub 驱动扩展，浏览器工具与 recipe 执行共用一份实现；DSH 额外拥有提示注入、技能目录、live 局面与抽屉审批——那是 harness 的能力，不可移植。切分见 [mcp.md](./mcp.md)。

### 2.1 会话从哪里来

会话属于 DSH（模型、循环、上下文都在那里）。扩展**不创建会话，只请求一个**：

```
侧边栏（当前标签页）── POST /client/task { text, tabId, includePage } ──► Hub ──► 插件
   ├─ hub.ownTab(sessionId, tabId)                  // 先要页面：别人的页在这里就失败，什么都没建
   ├─ ctx.agents.create({ sessionId, agentOptions: 默认模型, meta: { cwd: taskCwd } })
   ├─ 首条用户消息 = 页面上下文 + 文本（agent.followup）
   └─ 返回 sessionId；面板开始镜像这个会话
```

顺序是有意的：**先占页面，再建会话**。反过来会出现"会话建好了却没页面可跑"的空壳，而它会出现在 DSH 的会话列表里。建会话失败就把租约还回去；建好了但首条消息发不出去，就 `dispose()` 掉再还租约。

约束：

- **没有 DSH 就没有大脑**：DSH 未运行时明确报错，不在扩展里起 loop。
- **一个任务拥有一组标签页**（通常一个，可能多个）：归属走 Hub 租约，不靠"谁先点"。layer 的会话本来就支持多个标签（`shareTab`、`adoptTab`、页面打开的标签自动加入），缺的是 Hub 侧的 1:N 租约。
- **模型用部署默认**（`ctx.agentDefaultModel.currentSelection()`），要换再提供选择器。
- **工作区（cwd）必须有明确默认值**，不能是"DSH 碰巧的 cwd"。
- 这样创建的会话出现在 DSH 的会话列表里，可以继续在 DSH 里聊。

现状：N1（路由与会话创建）、N2（创建即绑定）、N3（侧边栏 `+`）、H8（租约是集合）、N4（面板按标签页认会话）、N8/N9（标签组与 chips）都已实现。归属在 Hub，视图在侧边栏。

### 2.2 分组是视图，归属是租约

**真相**：任务 → 标签页集合（Hub 租约 + layer 会话）。**视图**：Chrome 标签组，按任务染色、命名，方便调试时一眼看出"这堆页面属于哪个任务"。

规则：

- 归属不随分组变化：用户把标签拖进拖出组，任务仍然拥有它；要让页面离开任务，走显式的"从任务移除"。
- 生命周期：第一个标签加入时建组；页面打开的标签（`window.open`、`target=_blank`）自动加入；标签离开会话时移出；任务结束可解散空组。
- 谁来做：**侧边栏**。它同时握着两件事——Hub 报来的"哪个会话有哪些标签页、任务叫什么"，和浏览器里的标签页。Hub 在租约变化时把会话列表重发一遍，面板据此对齐分组，所以任务自己开的页面也会进组。
- 组名跟任务名走：组名来自会话标题，标题在第一条用户消息之后才有内容，所以组名会随标题更新一次。**不是本面板创建的组只认领、不改名**，用户手动改过的名字会保留。
- 面板关着时不做分组，也不做"移出组"：分组是视图，打开侧边栏时按当时的租约一次对齐，不会出现"面板没开，页面却自己跳组"。
- 一个组只能在一个窗口。当前实现只给**任务第一个标签所在窗口**的页面分组，同一任务在别的窗口的页面留在组外（chips 里仍然看得到）；每个窗口各分一组，留到真有人这么用时再做。
- 任务结束默认**保留标签页、解散组**，绝不关闭用户自己的页面；任务自己打开的页面可以显式"关闭本任务的页"。
- 权限：`chrome.tabs.group` 用现有的 `tabs` 权限即可；给组命名需要 `tabGroups`——已申请（`src/ui/manifest-permissions.ts`）。它本身不产生安装警告，旧产品也申请过；`PRIVACY.md` 与商店文案同步说明。
- 旧实现可以直接参考：`src/background/checks/panel-tabs.ts`（旧面板按会话分组：agent 打开的标签在后台入组、`@` 共享、拖出、删除会话时清理）。



## 3. 一次调用的数据流

1. 模型调用 `nanobrowser_click` 等工具。
2. 插件做租约检查（`lease-guard`），把参数交给 Hub。
3. Hub 再查一次租约（`needsLease()`，与 guard 同一处实现），入队；扩展下一次 `/poll` 取走，超时 20s 空轮询。Hub 这一层是权威的——MCP 客户端不经过 guard。
4. 扩展在对应标签页执行：快照或定位 → 分类是否敏感 → 必要时弹审批卡 → 派发 CDP 输入。
5. 结果（文本 + 结构化数据 + 错误码）回传 Hub，Hub 记审计，插件转成模型可读的结果。
6. 下一步的系统提示里出现 `Browser now:`（连接、租约与扩展实报的标签页、上次调用、失败原文）。页面身份不靠再查一次：扩展把结果所属的标签页（id、标题、URL）随 `/result` 一起报，Hub 按客户端存一份，提示组装是同步的。
7. 取消走另一条路：`/client/cancel` 让 Hub 立刻结束这次调用的等待，扩展在下一次 `/poll` 拿到 `cancel` 命令时**在入队那一刻就 abort 正在跑的那次调用**（队列是串行的，命令循环正忙在那次调用里，等它自己处理就来不及了）。效果是"还没派发的动作不会派发"，已经发给页面的输入不会撤回——这和 layer 的 invariant 3 一致。

审批发生在**派发之前**：写操作（submit/send/delete/upload）按"站点规则 → 模式"决定问不问；支付、授权、机密输入、页面 `prompt` 永远是用户自己的步骤，任何模式都不问也不代做。

## 4. 三个挡位（核心概念）

同一个 agent，按"这段路熟不熟"切换，而不是二选一。

| 挡位 | 触发条件 | 谁决策 | 上下文需求 | 停止策略 |
|---|---|---|---|---|
| **巡航** | 有可用 recipe、参数齐、页面匹配、上次成功 | agent 只传参 | 越少越好 | 失败即停 |
| **接管** | recipe 失败、断言不符、页面异常 | 模型 + SOP 知识 | 强：失败原文、局面、相关知识 | 诊断后决定续跑/换路/问人 |
| **探索** | 没有 recipe，或用户说"调试" | 模型，用户旁观 | 强：console / network / DOM / 截图 | 随时停，人可接手 |

换挡规则必须是显式的，否则模型会一直探索（慢、贵）或一直巡航（瞎跑）：

1. 巡航失败 → 进入接管；接管失败两次 → 停下来问用户。
2. 用户说"看看""调试""为什么" → 强制探索挡。
3. 探索成功一次并被用户认可 → 可沉淀为 recipe，下次巡航。

现状：巡航可用（失败即停，可 `until` 停在某步、`from` 接着跑，所以接管有落点）；接管缺知识召回（S5）；探索可用但成本高（每次都要重新问页面）。

## 5. 上下文模型

四层，按挡位注入，不搞"每步全量灌"。

| 层 | 内容 | 注入时机 | 预算 | 现状 |
|---|---|---|---|---|
| L0 规则 | 工具规则、租约、审批规则、页面内容是数据 | 系统提示固定段 | 短 | ✅ |
| L1 live 局面 | 连接、租约、上次调用成败与耗时、**失败原文**、页面 URL/标题、console error 数、network 失败数 | 每个模型步 | 中 | ✅ 页面身份由扩展随每个 `/result` 上报；失败原文取 Hub 缓存（600 字符）。console/network 计数仍未纳入 |
| L2 任务上下文 | 页面摘要、选中文本 | 用户从页面发消息时 | 4000 字符（选择 2000） | ✅ 不刷新，但来源被记下：L1 会指出"这条消息来自另一个页面" |
| L3 知识召回 | 与当前错误/URL 匹配的 SOP 段落 | 失败时、挡位切换时 | 小 | ❌ 未实现 |

原则：**只在岔路口看**（失败、跳转、断言不符），巡航不重看页面。21 步每步一次快照会烧掉几十万 token。

## 6. 记忆与知识

三种记忆，三种载体：

| 记忆 | 载体 | 生命周期 | 现状 |
|---|---|---|---|
| 会话内 | DSH transcript | 一个会话 | ✅ |
| 流程知识 | `SKILL.md`（手写 SOP）+ `recipe.json`（机器执行） | 长期、可 git | ✅ 手写；save 会覆盖 SKILL.md |
| 跨会话页面知识 | 站点笔记（site notes） | 长期 | ❌ 明确排除在首版外，需要决策是否破例 |

沉淀闭环：

- 成功路径 → recipe（`browser_skill_save` 录制，或手写）。
- 失败模式 → SOP 段落（现在只能手写；失败时既不召回，也不自动追加）。
- 一次性成功 → 可升格为 recipe 或 SOP。

单一事实源：**SOP 归人写，recipe 归机器执行**。`renderSkillMd` 生成的是渲染产物，不是知识；覆盖它等于删知识。

## 7. 执行模型

三个粒度：

| 粒度 | 载体 | 适合 | 不适合 |
|---|---|---|---|
| 动作 | layer 工具（18 个） | 探索、调试、一次性 | 重复、长流程 |
| 段落 | recipe（状态 A → 状态 B） | 固定路径、重复 | 需要判断的分支 |
| 全局 | 散文 skill / SOP | 判据、异常、组合、汇报 | 精确执行 |

recipe 是**状态转移器**，不是"任务"：`copy-order` = 列表 → 订单录入；`submit-order` = 任意 → 下单。组合靠状态衔接，不靠函数调用。

recipe v1 字段（现状）：`name` / `version` / `description` / `whenToUse` / `origin` / `params` / `steps` / `onFail` / `assert` / `createdFrom` / `needsReview` / `modelInvocable`。字段、步骤与断言的完整说明在 [reference.md](./reference.md) §5。

v1 的硬限制：

- 没有条件、没有循环（循环应在 agent 层做）。
- 没有回滚：已经派发的输入不会撤回（layer 的 invariant 3）。
- 步骤只能调用 9 个动作工具（navigate/click/set/type/press/hover/scroll/wait/handle_dialog），读类工具不能进流程。
- 没有 `note` 字段：JSON 写不了注释，解释放 `SKILL.md`。

这一版已经补齐的：断言四类（text 含 `absent`、URL、console 错误数、network 状态）、结构化失败（步号 + 码 + `delivered` + 原文 + 当前 URL）、从失败步续跑（`from`）、停在指定步（`until`）、失败策略（`onFail` 四动作，I1）、参数类型校验与可读值转换（`INVALID_PARAMS`）、批次（`batch`）。

录制与手写：以手写为准。录制器只保留"成功路径"，适合产出初稿；它把目标记成 role+name，**只覆盖带 `<!-- generated by browser_skill_save -->` 标记的 `SKILL.md`**，手写的那份原样保留。固定等待会被改写成条件等待：如果等待之后那一步有目标，就记成"等那个目标可见"，而不是"等 1.5 秒"；改不了的（后面没有目标）会在保存结果和每次运行的汇总里点出来。参数从表单字段推断（ASCII 字段名）。

### 7.1 手写体验（格式问题）

现状：21 步 JSON，没有注释，字段重复，参数没有校验——"格式在跟你作对"是真的。三个候选：

| 方案 | 好处 | 代价 |
|---|---|---|
| A 保持 JSON，每步加 `note`，id 稳定 | 零改动，机器安全 | 注释能力有限，长流程仍难读 |
| B 换成 YAML | 可注释、可读 | 新增依赖；缩进易错 |
| C `SKILL.md` 里放一个 fenced 可执行块，加载时编译成 recipe | 一份文件既是 SOP 又是宏；覆盖问题消失 | 解析成为关键路径；`SKILL.md` 手写错误会直接影响执行 |

**已选 A：保持 JSON**，理由见 [ADR 0005](./adr/0005-recipe-stays-json.md)。JSON 能 diff、能 review、`validateRecipe` 是唯一校验点；YAML 的缩进歧义（尤其带中文与多行文本时）会把"手写痛苦"换成"静默解析错"；内嵌块会让 `SKILL.md` 同时是散文和执行体，违背 ADR 0001。手写痛苦改由"录制器更聪明"来缓解——参数推断、条件等待、丢掉 ref 都在这条路上。

## 8. 授权模型

| 级别 | 机制 | 谁决定 | 现状 |
|---|---|---|---|
| 动作 | 扩展审批卡（写操作分类） | 用户 | ✅ |
| 敏感 | 支付/授权/机密/`prompt` 永不代做 | 用户，强制 | ✅ |
| 工具 | DSH 抽屉审批（allowed-once / delegate / rejected） | 用户 | ✅ |
| 站点 | 站点规则 allow / ask + 模式 auto | 用户 | ✅ |
| 技能 | `origin` 锁 + 写步骤仍审批 | 用户 | ✅ |
| 批次 | 一次授权覆盖一批订单（本任务授权，30 分钟，批次复用） | 用户 | ✅ |

原则：**agent 无法提高自己的权限**。批次授权也必须是一次性、可撤销、结束汇报，并且不能覆盖敏感动作。

## 9. 失败语义

三类失败，判定方式和默认动作不同：

| 类型 | 例子 | 判定者 | 默认动作 |
|---|---|---|---|
| 到不了 | 目标不存在、ref 失效、导航失败 | layer 错误码 + hint | 重新观察，再决定 |
| 没生效 | 点击被拦截、控件状态未变 | `INTERCEPTED` / `STATE_UNCHANGED` | **不要盲目重试**，先看页面 |
| 结果不对 | 提交被拦、静默失败、金额不对 | recipe 的 `assert`（文本在/不在、URL、console 错误数、network 状态） | 不满足就失败；写操作没断言则在汇总里明确"成功与否未知" |

layer 的每个错误码都带一句"下一步该做什么"（`DEFAULT_HINTS`），这是"聪明"的现成来源；插件必须保证这句话完整到达模型，而不是被截断。

runner 因此不再压缩失败步：`data.failure` 带 `code`、`delivered`、`hint`、`url`/`title`，文本里失败步的原文整段打印（只在超过 4000 字符时截断并明说）。`delivered` 是重试安全性的唯一依据——`false` 可以重试，`unknown` 必须先看页面。断言失败属于"结果不对"，它自己的 `delivered` 是 `unknown`：检查失败不代表那一步没生效。

### 9.1 失败策略写进 recipe（I1，已实现）

字段是 `onFail`：一张"码 → 动作"的表，recipe 级给默认，step 级覆盖同一张表。

```json
"onFail": { "USER_STEP": "ask", "*": "stop" }
```

```json
{ "id": "submit", "tool": "click", "target": { "role": "button", "name": "提交" },
  "onFail": { "INTERCEPTED": "report", "NO_MATCH": "skip", "*": "stop" } }
```

解析顺序：`step.onFail[code]` → `step.onFail["*"]` → `recipe.onFail[code]` → `recipe.onFail["*"]` → `"stop"`。`code` 取结果的 `error.code`（layer 的 35 个码）；断言失败用 runner 码（`ASSERT_*`）；两套码都在 [reference.md](./reference.md) §7 里。

四个动作：

| 动作 | 含义 | 结果 | 约束 |
|---|---|---|---|
| `stop` | 默认。停下并报失败 | `ok:false`，`outcome:"failed"` | — |
| `report` | 按 recipe 的意思这不是错误（"已经提交过"） | `ok:true`，`outcome:"reported"`，仍带 `data.failure` | — |
| `ask` | 停下来等人决定 | `ok:false`，`outcome:"asked"` | — |
| `skip` | 记一笔，继续下一步（可选步骤，例如"有弹窗就关掉"） | 继续 | **只在 `delivered: false` 时允许**，否则按 `stop` 处理 |

`skip` 的护栏是这张表里唯一真正危险的地方：layer 已经回答了"有没有东西到达页面"，`delivered` 不是 `false` 的时候跳过就是带着未知状态往前走，所以那时它降级成 `stop`——recipe 写了也不听。

### 9.2 失败时把 SOP 的对应段落交出去（I3，已实现）

知识继续留在 `SKILL.md`，用固定标题的一段：

```md
## When it fails

- `INTERCEPTED`: 页面在点击那一刻变了。重新快照，然后从 `submit` 续跑。
- `submit` + `ASSERT_TEXT`: 提交后没看到成功提示。先看页面，判断这笔是不是已经进去了。
- `USER_STEP`: 支付是用户自己的步骤，在面板里让他完成。
```

失败时 runner 做一次**确定性匹配**（不叫模型、不加 I/O：`skill.content` 从 `readSkill` 出来就已经在手上了）：取该段内的每条 bullet，正文里出现反引号包住的**失败码**或**步 id** 就算命中；最多取 3 条，原文附在失败文本的 `From the skill's own notes:` 之后，同时进 `data.knowledge`。

没有这一段、或一条都没命中，就什么都不加——**不凭空生成建议**。这条和 §9.1 的 `onFail` 是两个方向：`onFail` 让引擎**行动**，I3 让模型**知道**。

手写段落解决了"作者知道怎么失败"，剩下的是"机器自己遇到过的失败"。这一半由**学习闭环**补上（C5，已实现）：

- 每次**真跑**失败（`outcome: "failed"`，且失败在某个步上），runner 把这个失败写进该技能自己的记录：失败码 + 步 id + 那一步在做什么 + 页面原话 + 当时的 URL + 次数与首末时间。
- 下一次失败时，先读记录再匹配（码或步 id 一样算命中），命中过的按次数排序，最多 3 条，附在失败文本的 `Learned from earlier failures of this skill:` 之后，同时进 `data.learned`。手写段优先，占了位置时学到的只留 2 条。
- 记录放在**用户技能目录**的 `.knowledge/<name>.json`（不是技能目录里，也不改 `SKILL.md`，理由见 [ADR 0006](./adr/0006-learned-failures-are-a-sidecar.md)）。随仓库发布的内置技能是只读的，但同样能学。
- **不学的东西**：dry run（预检可以错在页面状态上）、取消、以及 `NO_LEASE`/`INVALID_RECIPE`/`INVALID_PARAMS`/`MISSING_PARAMS`/`SECRET_PARAM`/`ORIGIN_MISMATCH` 这类"说的是调用、不是页面"的失败。一条记录应该教技能下次少踩一次页面，而不是记一次调用写错。
- 写入是**尽力而为**：目录不可写时这次运行照常返回失败，不因为记录写不进去再错一次。

## 10. 安全与隐私

- `origin` 锁：recipe 只能在记录的站点运行。
- 机密不落盘：录制时跳过机密字段；含 `{{secret:*}}` 的 recipe 拒绝执行。
- 页面内容边界：页面文本只作为数据进入模型，带标记；不得被当作指令。
- 审批不可绕过：agent 不能关闭审批，也不能替用户完成支付/授权/机密。
- 数据出口：只有模型提供方能看到页面内容；`PRIVACY.md` 必须与实现同步。
- **Hub 拒绝网页来源**：任何 `Origin: http(s)…` 的请求（连 CORS 预检一起）直接 403，WebSocket 升级同样拒。原因很实在——token 默认是公开的 `dev-token`，靠它挡不住任何读过仓库的人；而浏览器一定会把网页自己的 Origin 带在跨源请求上，网页伪造不了、也去不掉。扩展页（`chrome-extension://`）和本机程序（Node，无 Origin）不受影响。
- **不做请求限速**（决定，不是遗漏）：Hub 只监听 `127.0.0.1`，只有一个队列、一个扩展在消耗它，队列随下一次轮询就清空；在只有一个消费者的情况下加限速只是给自己制造 429。真出现第二个消费者（比如两个 Hub 客户端抢同一个端口）时再谈。

## 12. 不做什么（v1）

- 不在扩展里放模型、密钥、agent loop。
- 不做第二套 MCP 能力：适配器只翻译，工具/技能/审批复用一个实现（见 [mcp.md](./mcp.md)）。
- 不支持 Chrome/Edge 之外的浏览器。
- 不做多 agent 协作、planner/navigator。
- 不做**站点笔记**（跨会话页面知识）：它是记忆的第一层，但没有"什么该记、谁来判断过时"的答案之前，记下来的多是噪音。失败已经结构化（码 + 原文 + 当前 URL），够人判断。
- 不把 recipe 变成可执行代码（安全面）。
- 不让模型自由执行 recipe 的每一步（确定性会消失）。
- 不对写操作做自动重试。

## 13. 术语

| 术语 | 含义 |
|---|---|
| 挡位 | 巡航 / 接管 / 探索，三种执行姿态 |
| 接管 | 模型在失败后按 SOP 接手，而不是继续盲跑 |
| recipe | 状态 A → B 的确定性步骤序列，机器执行 |
| SOP | 人写的知识：前提、判据、坑、失败怎么办 |
| 传送门 | 以"到达某状态"为目的的 recipe |
| live 局面 | 每个模型步注入的当前浏览器事实 |
| 批次 | 一次授权覆盖的一组同类操作 |

## 14. 已定的决策（留查）

原来放在这里的问题都已回答；没有还开着的。新的问题先放这里，答案定了再写成 [roadmap.md](./roadmap.md) 的一项。

1. **批量下单的授权粒度**：一次一张单。实现是**本任务**授权（内存、30 分钟上限、`detach`/重启即失效），`batch` 里第一单问一次、其余复用；不做"整批一次"的独立弹窗，也不把批次降级成站点级。
2. **跨会话页面知识（站点笔记）**：不做，理由见 §12。
3. **recipe 是否单独出现在技能目录**：不单独出现。技能以目录出现（`SKILL.md` + `recipe.json` 是一份技能的两个文件），`browser_skill_show` 才把 recipe 带出来；目录里显示步数与学到的条数，不显示 recipe 本身。
4. **"提交成功"的判据**：人写在 recipe 的 `assert` 里（文本/URL/console/network 四类），没断言的写操作在汇总里标记"成功与否未知"。**不加截图哈希**：它随主题、字体、分辨率变，值不可移植。
5. **recipe 的书写格式**：JSON，理由见 [ADR 0005](./adr/0005-recipe-stays-json.md)；手写痛苦走"录制器更聪明"这条路。
6. **仲裁规则写在哪**：两处都写。系统提示段（每次都在眼前）说"有技能就跑技能、失败后 `from` 续跑"；生成的 `SKILL.md` 里也写；手写 SOP 的失败段落由 §9.2 的召回接上。
