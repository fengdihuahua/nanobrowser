# ADR 0001：Browser Skill 是宏（macro），不是知识

- 状态：已采纳
- 日期：2026-11-04
- 相关：[design.md](../design.md) §4、§7

## 背景

插件通过 `ctx.skills.registerProvider()` 把 `recipe.json` 注册进 DSH 的技能目录，于是它和真正的 `SKILL.md` 技能出现在同一个 catalog 里。两者共用发现机制，但执行方式完全不同：真技能是给模型读的散文，Browser Skill 是给 runner 执行的步骤序列。

实际使用中，技能全部是**手写**的（`version` 已到 3/4，没有 `createdFrom`，`params` 是裸字面值），`SKILL.md` 里写的是页面行为知识（静默失败、加载态文案、固定顶栏遮挡、状态表、失败后怎么办）。录制器生成的内容一个都没用上，而保存时的 `renderSkillMd` 会覆盖手写内容。

## 决策

把 Browser Skill 定义为**宏**：

- `recipe.json` 是机器的执行脚本，管"状态 A → 状态 B"的确定性路径。
- `SKILL.md` 是人的 SOP，管前提、判据、坑、失败策略；它不是渲染产物。
- 模型只负责选择、传参、以及在失败时按 SOP 接管。

同时保留它在技能目录里的可发现性（可用 `/name` 触发），但在 `SKILL.md` 里明确"执行用 `browser_skill_run`，不要手动照抄步骤"。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把 recipe 做成可自由执行的散文 | 失去确定性、origin 锁与逐步审计；重复流程每次都要重新决策 |
| 让模型逐步执行 recipe 的每一步 | 等价于用模型替代 runner，慢、贵、不可复现 |
| 只保留散文技能，删掉 recipe | 21 步流程每次重跑，代价远高于维护 recipe |
| 继续以录制为唯一来源 | 产不出知识；且会覆盖手写 SOP |

## 后果

- 需要区分两个名字空间：传送门（recipe）与知识（SOP），避免同名抢占。
- 需要让失败时能召回 SOP 段落，否则 `SKILL.md` 只是摆设。
- 录制功能降级为"初稿生成器"，不再是主路径。
- `writeSkill` 覆盖 `SKILL.md` 的行为必须改：手写文件不能被自动生成物替换。
- **仲裁规则必须写进模型每次都能看到的地方**（系统提示段 + `SKILL.md` 头部）：正常路径只跑宏，宏停下时才按 SOP 接管。只在人脑里，模型就会读完 SOP 手动点，绕开断言与审批。
- **编排放在散文 skill，不进 recipe**：跨多个订单、跨系统、失败汇总由模型做；recipe 只负责一次页面内的固定段落，并把结构化结果交回去。
- 由此得到三条必须打通的接口（SOP → 引擎、recipe → 模型、模型 → SOP），见 [design.md](../design.md) §1.2。
