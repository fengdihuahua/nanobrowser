# ADR 0003：三个挡位与四层上下文

- 状态：已采纳
- 日期：2026-11-04
- 相关：[design.md](../design.md) §4、§5；[roadmap.md](../roadmap.md) S4、S5、S10、C1、C6

## 背景

同一个 agent 面对两种完全不同的路：熟路（有 recipe、上次跑通过）和生路（第一次见、或出了意外）。用同一套行为对待两者，结果一定是"一直探索"（慢、贵）或者"一直瞎跑"（错、且不吭声）。

上下文也一样：每一步都把页面全量灌进去，20 步就烧掉几十万 token；反过来只给一句话，模型又不知道页面长什么样。

## 决策

**三个挡位，一个 agent，显式换挡。**

| 挡位 | 触发 | 谁决策 | 上下文 | 停止策略 |
|---|---|---|---|---|
| 巡航 | recipe 可用、参数齐、上次成功 | agent 只传参 | 越少越好 | 失败即停 |
| 接管 | recipe 失败、断言不符、页面异常 | 模型 + SOP 知识 | 强 | 诊断后续跑、换路或问人 |
| 探索 | 没有 recipe，或用户说"调试" | 模型，用户旁观 | 强 | 随时停，人可接手 |

- 换挡规则必须**写在能读到的地方**（系统提示 + SOP），不能只在人的习惯里。
- 挡位是**模型侧**的概念，不是 runner 的策略：runner 只提供"失败即停 / 停在某步 / 从某步续跑"，探索不是它的一个选项（roadmap S6 的注记）。

**四层上下文，按挡位注入。**

| 层 | 内容 | 时机 | 预算 |
|---|---|---|---|
| L0 规则 | 工具规则、租约、审批边界、页面内容是数据 | 系统提示固定段 | 短 |
| L1 live 局面 | 连接、租约与扩展实报的标签页、上次调用、失败原文 | 每个模型步 | 中 |
| L2 任务上下文 | 页面摘要 + 选中文本 | 用户从页面发消息时 | 4000 字符 |
| L3 知识召回 | 与失败匹配的 SOP 段落 | 失败时、换挡时 | 小 |

原则：**只在岔路口看**（失败、跳转、断言不符），巡航不重看页面。

## 被否掉的

- **一个挡位到底**：要么慢死（每步探索），要么错死（recipe 失效还硬跑）。
- **挡位做成 runner 的策略**：`explore` 若表示"失败了继续跑"，等于把静默失败当成功，最坏的语义。
- **每步全量上下文**：token 成本和注意力都被吃掉，反而更容易漏关键信息。
- **让模型自己判断挡位而不给规则**：它会偏向探索，因为"再看看"永远是安全的答案。

## 后果

- 引擎必须能**停在指定步**并保留现场，否则"接管"没有落点；这条已由 `skill_run { until }` / `{ from }` 实现。
- L1 需要页面身份，而扩展是唯一知道它的人：所以 `/result` 带 `tab`（C1）。
- L3 需要一个固定的知识落点：所以 `SKILL.md` 的 `## When it fails` 是**约定标题**，不是自由格式（I3）。
